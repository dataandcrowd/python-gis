3.6. Bus Networks and Assignment 2

This is the last teaching section of Part 3. We close on a worked topic, the Auckland bus network, and finish with the brief for Assignment 2. Treat the bus network as a reference example: every technique here transfers to whichever topic you pick for your dashboard.

What you will learn

  • How to load and explore a GTFS feed in Python.
  • How to turn bus routes into a network graph for analysis.
  • How to wrap a multi-modal map in a Shiny app for shinylive.
  • The full Assignment 2 brief, marking criteria, and timeline.

GTFS in one paragraph

The General Transit Feed Specification (GTFS) is the standard format public transport agencies use to publish schedule data. A feed is a zip of CSV files: stops.txt, routes.txt, trips.txt, stop_times.txt, shapes.txt, plus a few others. For Auckland, the feed lives at Auckland Transport’s developer portal. For this section we will assume you have a copy in data/auckland_gtfs.zip.

Loading a GTFS feed with gtfs_kit

gtfs_kit is a small Python library that handles the boilerplate of opening a feed, computing schedules, and producing GeoDataFrames.

uv add gtfs-kit
import gtfs_kit as gk

feed = gk.read_feed("data/auckland_gtfs.zip", dist_units="km")

print(f"Routes: {len(feed.routes)}")
print(f"Stops:  {len(feed.stops)}")
print(f"Trips:  {len(feed.trips)}")

Two operations you will use most:

# Geometry of every route as a GeoDataFrame
routes_gdf = feed.get_routes_gdf()

# Stops as a GeoDataFrame
stops_gdf = feed.get_stops_gdf()

For a Shiny app, save these once to GeoPackage (routes_gdf.to_file("routes.gpkg")) and load them at module level. GTFS parsing is too slow to do every time the app starts.

Treating the bus network as a graph

Stops are nodes; route segments between consecutive stops are edges. NetworkX makes this straightforward:

import networkx as nx

def build_bus_graph(feed):
    G = nx.DiGraph()
    st = feed.stop_times.sort_values(["trip_id", "stop_sequence"])
    for trip_id, group in st.groupby("trip_id"):
        stops = group["stop_id"].tolist()
        for a, b in zip(stops[:-1], stops[1:]):
            if G.has_edge(a, b):
                G[a][b]["trips"] += 1
            else:
                G.add_edge(a, b, trips=1)
    return G

The trips attribute on each edge counts how many scheduled trips pass over that segment. High-trip edges are the trunk corridors (Dominion Rd, New North Rd, Great South Rd in Auckland). This is one cheap-and-cheerful proxy for “how important is this segment”.

Centrality measures, briefly

NetworkX gives you nx.betweenness_centrality(G), nx.closeness_centrality(G), and nx.degree_centrality(G). Each tells a different story about which stops are important. Betweenness flags transfer hubs; closeness flags accessibility; degree flags interchanges. Pick the one that matches your dashboard’s question, not all three.

Wrapping it in a Shiny app

A small Shiny app for exploring routes by frequency:

from shiny import App, ui, render, reactive
from shinywidgets import output_widget, render_widget
from ipyleaflet import Map, GeoData
import geopandas as gpd

routes_gdf = gpd.read_file("data/auckland_routes.gpkg")  # precomputed

app_ui = ui.page_sidebar(
    ui.sidebar(
        ui.input_slider("min_trips", "Minimum daily trips",
                        0, int(routes_gdf["trips"].max()), 0, step=10),
        ui.input_select("route_type", "Route type",
                        choices=["All", "Bus", "Train", "Ferry"]),
    ),
    ui.card(
        ui.card_header("Auckland bus network"),
        output_widget("map"),
    ),
    title="AT route explorer",
)

def server(input, output, session):

    @reactive.calc
    def filtered():
        df = routes_gdf[routes_gdf["trips"] >= input.min_trips()]
        if input.route_type() != "All":
            df = df[df["route_type"] == input.route_type()]
        return df

    @render_widget
    def map():
        m = Map(center=(-36.85, 174.77), zoom=11)
        m.add_layer(GeoData(geo_dataframe=filtered(),
                            style={"color": "#d73027", "weight": 2}))
        return m

app = App(app_ui, server)

Same skeleton as 3.4. New bit: a real-world dataset and a meaningful filter (“how does the network look if I keep only routes with at least N trips a day?”). That kind of question is what makes a dashboard worth deploying.

Common pitfalls with GTFS in shinylive

  • File size. A full GTFS for Auckland is several MB. Aggregate to a daily summary (one row per route) before saving the GeoPackage.
  • Time of day. “Trips per day” hides peak-vs-off-peak. If your assignment is about congestion, slice by hour.
  • Direction. Stops are not symmetric; route shapes are directional. Check that you are not double-counting.
  • Holiday calendars. GTFS distinguishes weekday, Saturday, Sunday, and special services. Decide once which calendar you are using and stick to it.

Assignment 2 Brief

Due: Friday 8 May 2026 (end of Week 8), 23:59 NZST. Weight: 30% of the course mark. Format: a deployed shinylive URL plus a public GitHub repo.

What you must build

A Shiny dashboard that addresses one urban-analytics question about Auckland (or another New Zealand city, with permission). The question must be specific enough that someone could disagree with your answer.

Examples of acceptable questions:

  • “Which Auckland suburbs have the worst evening peak congestion, and how much would removing one lane on Dominion Rd change that?”
  • “How does bus accessibility to the city centre vary by suburb, and which areas are worst served?”
  • “Where in central Auckland are pedestrian volumes highest relative to footpath capacity?”
  • “Which neighbourhoods in the isthmus have the lowest green-space accessibility within a 15-minute walk?”

Required components

The dashboard must include all of the following.

  1. Three or more pages built with ui.navset_tab or ui.page_navbar. Suggested split: Overview, Map, Data, About.
  2. An interactive map with at least two user-controlled filters. ipyleaflet preferred (so it deploys to shinylive); folium is fine if you ship a traditional Shiny app.
  3. A temporal or comparative element. Either a time-period filter (date range, hour-of-day) or a side-by-side comparison (two suburbs, two scenarios, before/after).
  4. At least one reactive expression with @reactive.calc, shared between two or more outputs.
  5. At least one @reactive.event or @reactive.effect doing something useful (a Reset button, a save-snapshot button, a “Recompute” gate on an expensive operation).
  6. A polished UI using ui.page_sidebar, ui.card, and a shinyswatch theme.
  7. Deployment to a public URL, either via shinylive on GitHub Pages, or a traditional Shiny deployment.
  8. A README in the repo with: project description, data sources, how to run locally, deployed URL, and known limitations.

On data ethics

Anything you put into a shinylive bundle is downloaded by every user. Do not ship anything you would not put on a public website. If your data contains personal information, aggregate before bundling.
