3.5. Routing and Congestion

Part 3 so far has been about Shiny itself. From here to the end of the chapter we shift to the content that goes into your Assignment 2 dashboard. Routing and congestion first (this section), bus networks next (3.6).

The Shiny pieces you already know are enough. The new material is four ideas from transport analytics: travel time, the Travel Time Index, the Volume/Capacity ratio, and Level of Service. We will implement each as a small function, then wrap the lot in a Shiny app.

What you will learn

  • The origin-destination (OD) framing transport analysts use.
  • Three common congestion indicators (TTI, V/C ratio, LOS) and how to compute them.
  • How to surface those indicators in a small Shiny dashboard.

The OD framing in one paragraph

Transport analysis starts from pairs: an origin (where a trip starts) and a destination (where it ends). Between them there is at least one route, chosen by the traveller based on time, cost, and habit, and constrained by the network (one-way streets, turn bans, closures). Almost every congestion indicator is a function of either a route or a network edge. Keep this shape in mind.

Travel time

The simplest indicator. Two versions of it.

Free-flow travel time is how long a trip takes with no delays, at the speed limit:

def free_flow_minutes(distance_m: float, speed_kmh: float) -> float:
    return (distance_m / 1000) / speed_kmh * 60

Actual travel time comes from observation (GPS traces, INRIX, Google Maps API, TomTom) or simulation (r5py, OSRM). For the worked example we will fake it.

The Travel Time Index (TTI)

TTI is the ratio of actual to free-flow travel time. It tells you how much longer a trip is than it “should” be.

def tti(actual_min: float, free_flow_min: float) -> float:
    if free_flow_min == 0:
        return float("nan")
    return actual_min / free_flow_min

Reading the value:

  • TTI = 1.0: no delay.
  • TTI = 1.2: 20% longer than free flow.
  • TTI = 1.5: severely congested.
  • TTI = 2.0: gridlock.

The Volume-to-Capacity ratio (V/C)

V/C compares traffic volume on a road to the road’s capacity. Unlike TTI, which is measured per trip, V/C is measured per link (road segment) per time period.

def vc_ratio(volume_vph: float, capacity_vph: float) -> float:
    if capacity_vph == 0:
        return float("nan")
    return volume_vph / capacity_vph

And the conventional Level of Service (LOS) classification:

def level_of_service(vc: float) -> str:
    if vc < 0.60: return "A"
    if vc < 0.70: return "B"
    if vc < 0.80: return "C"
    if vc < 0.90: return "D"
    if vc < 1.00: return "E"
    return "F"

A is free flow; F is forced flow (stop-and-go). Anything at C or worse is worth flagging in a dashboard.

A small Shiny app showing link-level congestion

Here is a minimal dashboard using the functions above. The data is a tiny fake “network” of five corridors. Swap it for your own OSMnx-derived data when you are ready.

from shiny import App, ui, render, reactive
from shiny.render import DataGrid
import pandas as pd

# Five pretend corridors
links = pd.DataFrame({
    "corridor": ["Queen St", "Ponsonby Rd", "Great North Rd", "Broadway", "Symonds St"],
    "length_m":   [1200, 2100, 3400, 1800, 900],
    "speed_kmh":  [30, 50, 50, 50, 40],
    "capacity":   [1800, 2000, 2200, 1800, 1600],
})

def free_flow_minutes(distance_m, speed_kmh):
    return (distance_m / 1000) / speed_kmh * 60

def tti(actual, free_flow):
    return actual / free_flow if free_flow else float("nan")

def level_of_service(vc):
    for thr, letter in [(0.6, "A"), (0.7, "B"), (0.8, "C"), (0.9, "D"), (1.0, "E")]:
        if vc < thr:
            return letter
    return "F"

app_ui = ui.page_sidebar(
    ui.sidebar(
        ui.input_slider("volume_pct", "Traffic volume (% of capacity)", 30, 130, 80, step=5),
        ui.input_slider("delay_pct", "Travel time inflation vs free flow (%)", 0, 150, 30, step=5),
    ),
    ui.card(
        ui.card_header("Corridor indicators"),
        ui.output_data_frame("tbl"),
    ),
    title="Auckland corridor congestion (demo)",
)

def server(input, output, session):

    @reactive.calc
    def indicators():
        df = links.copy()
        df["free_flow_min"] = free_flow_minutes(df["length_m"], df["speed_kmh"])
        df["actual_min"]    = df["free_flow_min"] * (1 + input.delay_pct() / 100)
        df["tti"]           = df["actual_min"] / df["free_flow_min"]
        df["volume"]        = df["capacity"] * input.volume_pct() / 100
        df["vc"]            = df["volume"] / df["capacity"]
        df["los"]           = df["vc"].apply(level_of_service)
        return df.round({"free_flow_min": 1, "actual_min": 1, "tti": 2, "vc": 2})

    @render.data_frame
    def tbl():
        return DataGrid(indicators(), filters=True, width="100%")

app = App(app_ui, server)

Try it: move the two sliders and watch the indicators change. Both inputs feed a single @reactive.calc; the table is the only observer. That is the pattern from 3.3, applied to a transport problem.

Where real data comes from

The fake numbers above will not convince anyone. For Assignment 2 you will want one of:

  • Auckland Transport counts: vehicle and pedestrian counts at specific intersections, available via the AT Open Data portal.
  • Waka Kotahi (NZTA): state highway counts and travel-time monitoring.
  • OpenStreetMap, via OSMnx: network geometry, speed limits, highway classes. Good for building the baseline; poor for real volumes.
  • r5py: routing and travel-time matrices computed from OSM + GTFS. Powerful but it needs Java and it does not run in Pyodide, so you will have to precompute results and ship the outputs with your app.

For the dashboard, precompute indicators in a notebook, save the result as a GeoPackage or GeoJSON, and load that file from the app. Keep the Shiny app small and the heavy lifting upstream.

The r5py sketch, for reference

If you want to try a proper travel-time calculation offline, r5py’s flow is: build a TransportNetwork from an OSM extract and (optionally) a GTFS zip, define origins and destinations as GeoDataFrames, hand both to TravelTimeMatrixComputer, pick a departure time and set of modes, and call compute_travel_times(). Save the resulting matrix as Parquet or CSV and load it from the Shiny app later.

Mapping the result

The table is useful but a map is better. Join the indicators() result to a GeoDataFrame of the corridor geometries and render with ipyleaflet. Colour edges by V/C or LOS. Pseudocode:

# Outside the app, one-off
corridors_gdf = gpd.read_file("auckland_corridors.gpkg")

# Inside the server
@render_widget
def corridor_map():
    df = indicators()
    gdf = corridors_gdf.merge(df, on="corridor")
    m = Map(center=(-36.85, 174.77), zoom=12)
    for _, row in gdf.iterrows():
        colour = {"A": "#1a9850", "B": "#91cf60", "C": "#d9ef8b",
                  "D": "#fee08b", "E": "#fc8d59", "F": "#d73027"}[row["los"]]
        m.add_layer(GeoData(geo_dataframe=gpd.GeoDataFrame([row]),
                            style={"color": colour, "weight": 4}))
    return m

You will refine the colour mapping and the legend, but the shape of the solution is: precomputed geometries, reactive indicators, joined at render time.

What you have learned

  • Transport analysis uses an origin-destination framing; indicators are computed per trip or per link.
  • Three workhorse indicators: travel time (free-flow vs actual), TTI, and V/C with a LOS grade.
  • You can wrap any of these in a Shiny app with one reactive calc and one output.
  • Precompute heavy routing offline and ship the result; keep the Shiny app light.
