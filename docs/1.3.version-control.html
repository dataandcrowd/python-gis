1.3 Version control with Git

Story problem

Explaining why your Auckland results changed

You’re analysing transport accessibility in Auckland. You run your script on Monday and get a certain result. On Friday, you run the same script and the map looks completely different.

Questions arise: - What changed? - Which version was correct? - Can you go back to Monday’s version? - How do you collaborate without overwriting each other’s work?

Answer: Git tracks every change and becomes your research diary.

What you will learn

  • Understand what Git is and why it matters
  • Use commit, branch, push, pull in practice
  • Structure a Git repository for a GIS project
  • Collaborate using GitHub
  • Avoid committing large or sensitive data

Understanding version control

The problem: Manual version control

Without Git, people often do this:

project/
├── analysis.py
├── analysis_v2.py
├── analysis_final.py
├── analysis_final_REALLY.py
├── analysis_final_2024-01-15.py
└── analysis_final_after_supervisor_comments.py

Problems: - Which version is actually the latest? - What changed between versions? - How do you merge two versions? - How do you collaborate?

The solution: Git

Git tracks every change in a structured way:

project/
└── analysis.py  ← One file, entire history tracked

Git history:
├── 2024-01-10: "Initial analysis script"
├── 2024-01-12: "Fixed coordinate projection bug"
├── 2024-01-15: "Added population weighting"
└── 2024-01-18: "Implemented supervisor's feedback"

Benefits: - Complete history of every change - See exactly what changed when - Revert to any previous version - Multiple people can work simultaneously - Collaborate via GitHub/GitLab

Core Git concepts

Repository (repo)

A project tracked by Git. Contains: - Your files - Complete history of changes - Branches for parallel work

Commit

A snapshot of your project at a specific time. Think of it as saving a checkpoint in a video game.

Commit = snapshot + message + author + timestamp

Branch

A parallel line of development. The default branch is usually main.

main:    A → B → C → D
                  ↓
feature:          E → F

Remote

A version of your repository hosted online (e.g., GitHub). Enables: - Backup - Collaboration - Sharing

Writing good commit messages

Good messages: - ✅ “Add data loading function for shapefile import” - ✅ “Fix coordinate projection bug in Auckland layer” - ✅ “Update analysis to include 2024 census data”

Bad messages: - ❌ “Update” - ❌ “Fix stuff” - ❌ “asdfasdf”

Git workflow

The cycle: Edit → Stage → Commit

┌─────────────┐
│  Working    │  ← Edit your files
│  Directory  │
└──────┬──────┘
       │ git add
       ▼
┌─────────────┐
│   Staging   │  ← Files ready to commit
│     Area    │
└──────┬──────┘
       │ git commit
       ▼
┌─────────────┐
│  Repository │  ← Permanent snapshot
│   (History) │
└─────────────┘

Branching

Why branches?

Branches let you: - Experiment without breaking working code - Work on features in parallel - Collaborate without conflicts

Create a branch

git branch feature-add-population

Switch to branch

git checkout feature-add-population

Or create and switch in one command:

git checkout -b feature-add-population

Collaborating with Git

Clone a repository

Your colleague wants to work on the project:

git clone https://github.com/yourusername/auckland-greenspaces.git
cd auckland-greenspaces

They now have a complete copy, including all history.

Pull latest changes

Before starting work, always pull:

git pull

This downloads new commits from GitHub.

Push your changes

After committing locally:

git push

This uploads your commits to GitHub.

Typical collaborative workflow

# Start of day
git pull                    # Get latest changes

# Work
# ... edit files ...
git add .
git commit -m "Your changes"

# End of day
git pull                    # Get any changes from colleagues
git push                    # Share your changes

Repository structure for GIS projects

Recommended structure

auckland-transport-study/
├── .git/                   # Git history (hidden)
├── .gitignore             # Ignored files
├── .venv/                 # Virtual environment (ignored)
├── README.md              # Project documentation
├── pyproject.toml         # Dependencies (tracked)
├── uv.lock               # Locked versions (tracked)
├── data/
│   ├── README.md         # Data sources and descriptions
│   ├── raw/              # Original data (ignored if large)
│   └── processed/        # Cleaned data (tracked if <10MB)
├── src/                  # Python source code (tracked)
│   ├── __init__.py
│   ├── data_loader.py
│   ├── analysis.py
│   └── visualisation.py
├── notebooks/            # Jupyter notebooks (tracked)
│   ├── 01-exploration.ipynb
│   └── 02-analysis.ipynb
├── tests/                # Unit tests (tracked)
│   └── test_analysis.py
├── outputs/              # Generated files (ignored)
│   ├── figures/
│   └── tables/
├── reports/              # Reports and papers (tracked)
│   └── draft.qmd
└── docs/                 # Documentation (tracked)
    └── methodology.md

What to commit vs ignore

Commit (track in Git): - ✅ Source code (.py, .R, .qmd) - ✅ Configuration (pyproject.toml, uv.lock) - ✅ Documentation (README.md, .md files) - ✅ Small data files (<10MB) - ✅ Jupyter notebooks (carefully - see note below) - ✅ Analysis results (if reproducible and small)

Ignore (add to .gitignore): - ❌ Virtual environments (.venv/) - ❌ Large data files (>10MB) - ❌ Binary outputs (.png, .pdf, .html) - ❌ Cache files (__pycache__/, .ipynb_checkpoints/) - ❌ Credentials and API keys - ❌ Personal IDE settings

Jupyter notebooks

Notebooks can be tricky because they contain outputs. Options:

  1. Clear outputs before committing:

    jupyter nbconvert --clear-output --inplace notebook.ipynb

  2. Use version control for notebooks:

    uv add nbstripout
nbstripout --install

    This automatically clears outputs on commit.

Best practices

1. Commit often

Make small, focused commits:

# Good: small focused commits
git commit -m "Add function to load shapefile"
git commit -m "Fix projection to NZGD2000"
git commit -m "Add docstrings to data_loader.py"

# Bad: one huge commit
git commit -m "Add everything"

2. Write meaningful commit messages

Format:

<type>: <short description>

<optional detailed description>

Types: - feat: New feature - fix: Bug fix - docs: Documentation - refactor: Code restructuring - test: Adding tests - data: Data updates

Examples:

git commit -m "feat: add population weighting to accessibility analysis"

git commit -m "fix: correct EPSG code for Auckland projection"

git commit -m "docs: update README with installation instructions"

3. Pull before you push

Always pull before pushing:

git pull
# Resolve any conflicts
git push

4. Use branches for experiments

# Create branch for risky changes
git checkout -b experiment-new-method

# If it works:
git checkout main
git merge experiment-new-method

# If it doesn't work:
git checkout main
git branch -D experiment-new-method  # Delete without merging

5. Never commit sensitive data

Never commit: - Passwords - API keys - Database credentials - Personal data

Use environment variables instead:

# Bad
api_key = "sk-abc123def456..."  # Never hardcode!

# Good
import os
api_key = os.getenv('OPENAI_API_KEY')

Store in .env (which is in .gitignore):

OPENAI_API_KEY=sk-abc123def456...

Advanced: Undoing changes

Discard uncommitted changes

git checkout -- filename.py  # Discard changes to one file
git checkout -- .           # Discard all changes

Undo last commit (keep changes)

git reset --soft HEAD~1

Undo last commit (discard changes)

git reset --hard HEAD~1
Warning

git reset --hard permanently deletes changes. Use with caution!

Revert a commit (safe)

git revert a1b2c3d

This creates a new commit that undoes the changes.

Troubleshooting

Merge conflicts

Problem: Git can’t automatically merge changes

Solution: 1. Open conflicted files (marked with <<<<<<<, =======, >>>>>>>) 2. Manually resolve conflicts 3. Remove conflict markers 4. Stage and commit: bash git add . git commit -m "Resolve merge conflict"

Screenshot placeholder

[SCREENSHOT NEEDED: VS Code showing merge conflict with conflict markers]

Accidentally committed large file

Problem: Committed a 500MB GeoTIFF

Solution:

# Remove from Git but keep file locally
git rm --cached large_file.tif

# Add to .gitignore
echo "*.tif" >> .gitignore

# Commit the removal
git commit -m "Remove large TIF file from Git"

Authentication failures

Problem: GitHub rejecting password

Solution: Use Personal Access Token (see earlier section)

Detached HEAD state

Problem: You are in 'detached HEAD' state

Solution:

git checkout main  # Return to main branch

Quick reference

# Setup
git init                              # Initialise repository
git config --global user.name "Name"
git config --global user.email "email"

# Basic workflow
git status                            # Check status
git add .                            # Stage all changes
git commit -m "message"              # Commit with message
git log                              # View history

# Branching
git branch feature-name              # Create branch
git checkout feature-name            # Switch to branch
git checkout -b feature-name         # Create and switch
git merge feature-name               # Merge branch

# Remote (GitHub)
git remote add origin <url>          # Connect to GitHub
git push -u origin main              # First push
git push                             # Subsequent pushes
git pull                             # Download changes
git clone <url>                      # Clone repository

# Undoing
git checkout -- file                 # Discard changes
git reset --soft HEAD~1              # Undo last commit
git revert <commit>                  # Safe undo
