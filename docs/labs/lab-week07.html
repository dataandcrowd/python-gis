Lab Week 07

Overview

There is no lecture this week. This is a two-hour lab run by your two GTAs. Put a post on Ed Discussion if you have a question.

The goal is simple: plan before you code, then start building. By the end of the lab you will have a written planning document (three short sections), an ipyleaflet map rendering inside your Shiny app, and at least one action button wired up. The planning document feeds directly into your design report, so nothing you write today is throwaway work.

What you need:

  • Your track assignment confirmed (Track A, B, or C).
  • Your own dataset downloaded from the sources listed in 3.6 and saved under data/.
  • The Week 6 repo with a working hello-world Shiny app.
  • A text editor or Quarto document open for writing the plan.
Where to write the plan

Create a file called plan.md (or plan.qmd) in the root of your project repo. You will copy the best parts of this into your design report later. Writing it now, while the decisions are fresh, saves you time in Week 8.

Section 1: Motivation and audience

Answer the following questions in two to four paragraphs. Be specific; “Auckland residents” is too broad.

1.1 What problem does your dashboard address?

State the question your dashboard will help someone answer. Good questions are narrow enough that a single dashboard can answer them convincingly:

  • Track A example: “How has public transport patronage in Auckland recovered since 2020, and which modes are recovering fastest?”
  • Track B example: “Do workers and university students from the same origin SA2 commute to the same destinations, or do their travel patterns diverge?”
  • Track C example: “Where in Auckland are serious and fatal crashes concentrated, and has the spatial pattern shifted over the past five years?”

Write your own question. Do not copy the examples above.

1.2 Who is it for?

Describe one or two realistic users. What role do they hold? What decision would this dashboard inform? For example, a transport planner at Auckland Transport evaluating whether to increase frequency on a bus route, or a public health researcher comparing active-transport crash risk across suburbs.

1.3 What insight does it enable?

In one sentence, state the single most important thing a user should take away after spending two minutes with your dashboard. This sentence will likely become the title or subtitle of your app.

Why this matters for the rubric

The “Question” criterion (10%) rewards dashboards that address a clear, well-scoped question. Writing it down now, before you touch the code, prevents the common mistake of building a dashboard that shows data but does not answer anything.

Section 2: Data and preparation

2.1 Datasets used

Fill in a table like this for every dataset you plan to use (you need at least two):

Dataset Source URL Format Rows (approx.) Key variables you will use
e.g. AT patronage https://at.govt.nz/... CSV ~2,400 month, mode, boardings
e.g. Bus routes AT GIS open data GeoJSON ~300 route_short_name, geometry

2.2 Cleaning and preparation steps

For each dataset, list the steps you need to take before it is ready for the app. Be concrete:

  • Which columns will you keep? Which will you drop?
  • Do you need to melt, pivot, merge, or aggregate?
  • What is the original CRS? Do you need to reproject to EPSG:4326 for ipyleaflet?
  • Do you need to simplify geometries to keep the file size small for shinylive?

Write this as a numbered list. Each step should be one line.

2.3 Limitations

Every dataset has gaps. Note at least two limitations, for example: “Patronage data is monthly, so I cannot show weekly patterns” or “The crash dataset does not distinguish between crashes involving cyclists and those involving e-scooter riders”.

Acknowledging limitations early shows the marker that you understand your data, and it will become a paragraph in your design report.

Do the preparation now, not later

Open your dataset in a notebook. Run .head(), .dtypes, .columns, .shape. Fill in the table above with actual column names and row counts, not guesses. If the data is not what you expected, now is the time to find a better source or adjust your question.

Section 3: Technical architecture

3.1 App structure

Write the following in your plan.md (or plan.qmd). Start by deciding which top-level layout you will use (ui.page_sidebar or ui.page_navbar), then list every input and every output by name. This becomes the skeleton you will paste into app.py in Section 4.

Here is an example for Track B (do not copy it, write your own for your track):

# plan.md -- app structure sketch (Track B example)
#
# Layout: ui.page_sidebar
#
# Sidebar inputs:
#   ui.input_select("origin", ...)       -- pick an SA2
#   ui.input_checkbox_group("pops", ...) -- worker / student
#   ui.input_slider("top_n", ...)        -- how many destinations
#   ui.input_action_button("apply", ...) -- apply filters

# Main area outputs:

#   card 3: @render.text  "summary" -- "X workers, Y students from this origin"

Once you have this list, translating it into real app.py code is mechanical: each line becomes one ui.input_* or one ui.output_* / output_widget call.

Your diagram must include:

  • All three required inputs (with their ui.input_* type).
  • At least one @reactive.calc that is shared by two or more outputs.
  • The map output (@render_widget) and the chart output (@render.plot or @render_widget).

3.3 Key functions

List the two or three most important functions you will write (besides the ones Shiny gives you). For each one, write a one-line docstring. For example:

  • prep_patronage(raw_df, modes, year_from): filter patronage data by selected modes and start year, return a tidy DataFrame.
  • colour_by_severity(severity): return a hex colour string for a crash severity level.

3.4 Performance considerations

shinylive runs in the browser via Pyodide. Large files and heavy computation will make the app slow to load. Note any steps you will take to keep things fast:

  • Target file size for data/ folder (aim for under 2 MB total).
  • Geometry simplification tolerance.
  • Whether you will cap the number of rendered map markers.
  • Whether you will use @reactive.event to gate an expensive calculation behind a button.

Section 4: ipyleaflet maps inside Shiny

Now that the plan is written, start building. This section shows you how to get an ipyleaflet map into your Shiny app for each track. All examples use indicative column names; adapt them to your actual data.

The basic pattern

Every track uses the same wiring. In the UI, use output_widget from shinywidgets. In the server, use @render_widget and return a new Map object each time the reactive inputs change.

from shiny import App, ui, render, reactive
from shinywidgets import output_widget, render_widget
from ipyleaflet import Map, GeoData
import geopandas as gpd

gdf = gpd.read_file("data/your_file.geojson").to_crs(4326)

app_ui = ui.page_sidebar(
    ui.sidebar(
        ui.input_select("category", "Category",
                        choices=["All"] + sorted(gdf["category"].unique().tolist())),
    ),
    output_widget("map"),
    title="My dashboard",
)

def server(input, output, session):

    @reactive.calc
    def filtered():
        if input.category() == "All":
            return gdf
        return gdf[gdf["category"] == input.category()]

    @render_widget
    def map():
        m = Map(center=(-36.85, 174.77), zoom=11)
        m.add_layer(GeoData(
            geo_dataframe=filtered(),
            style={"color": "#1f78b4", "weight": 2, "fillOpacity": 0.4},
        ))
        return m

app = App(app_ui, server)

Two rules that prevent silent failures:

  • Always .to_crs(4326) when you load the GeoDataFrame. ipyleaflet expects WGS84; NZTM data will render as an empty map with no error.
  • Return a new Map() inside @render_widget every time. Do not create the Map at module level and try to mutate it; the widget will not update.
  • Track A: Public Transport
  • Track B: Commuter and Student OD
  • Track C: Auckland Crashes

Your map should show bus or ferry routes (lines). Use GeoData with a LineString GeoDataFrame. Wire a checkbox_group for transport modes so the user can toggle bus, train, and ferry layers.

from ipyleaflet import Map, GeoData
import geopandas as gpd

routes = gpd.read_file("data/routes.geojson").to_crs(4326)

@reactive.calc
def filtered_routes():
    return routes[routes["mode"].isin(input.modes())]

@render_widget
def map():
    m = Map(center=(-36.85, 174.77), zoom=11)
    sub = filtered_routes()
    if not sub.empty:
        m.add_layer(GeoData(
            geo_dataframe=sub,
            style={"color": "#d73027", "weight": 2, "opacity": 0.7},
            name="Routes",
        ))
    return m

To highlight a single route selected from a dropdown, add a second GeoData layer in a different colour:

@render_widget
def map():
    m = Map(center=(-36.85, 174.77), zoom=11)
    # all routes, dimmed
    m.add_layer(GeoData(
        geo_dataframe=filtered_routes(),
        style={"color": "#bdbdbd", "weight": 1, "opacity": 0.4},
    ))
    # selected route, bright
    sel = filtered_routes()
    sel = sel[sel["route_short_name"] == input.route()]
    if not sel.empty:
        m.add_layer(GeoData(
            geo_dataframe=sel,
            style={"color": "#e31a1c", "weight": 4, "opacity": 1.0},
        ))
    return m

            radius=4,
            color=severity_colours.get(row["severity"], "#636363"),
            fill_color=severity_colours.get(row["severity"], "#636363"),
            fill_opacity=0.7,
            weight=1,

    m.add_layer(LayerGroup(layers=tuple(markers)))
    return m
Why .head(2000)?

Each CircleMarker is a separate JavaScript object in the browser. Rendering 20,000 of them will freeze the page. Start with 2,000 and increase only if performance is acceptable. For the final submission, consider aggregating to a grid or using a heatmap layer instead.

Section 5: Adding an action button

An action button lets the user control when an expensive operation runs, instead of the app recalculating on every slider tick. This is the @reactive.event pattern from the lecture.

Step 1: Add the button to the UI

Place it at the bottom of your sidebar, after all the filter inputs:

ui.sidebar(
    ui.input_select("category", "Category", choices=[...]),
    ui.input_slider("min_value", "Minimum", 0, 100, 0),
    ui.input_checkbox_group("modes", "Modes", choices=[...]),
    ui.input_action_button("apply", "Apply filters"),
)

Step 2: Gate the reactive calc

Wrap your shared @reactive.calc with @reactive.event so it only recalculates when the button is clicked:

@reactive.calc
@reactive.event(input.apply)
def filtered():
    df = data.copy()
    if input.category() != "All":
        df = df[df["category"] == input.category()]
    df = df[df["value"] >= input.min_value()]
    return df

Now the user can adjust multiple inputs, then click “Apply filters” once. The map and chart update together, and only once.

Step 3: Add a reset button (optional but useful)

# In the UI, next to the apply button:
ui.input_action_button("reset", "Reset"),

# In the server:
@reactive.effect
@reactive.event(input.reset)
def _():
    ui.update_select("category", selected="All")
    ui.update_slider("min_value", value=0)
    ui.update_checkbox_group("modes", selected=modes)

ui.update_* functions push new values into the inputs from the server side. Combined with @reactive.event, the reset click restores defaults and the apply click picks them up.

Step 4: Show a summary line

Add a text output that tells the user what the current filter produced:

# UI
ui.output_text("summary"),

# Server
@render.text
def summary():
    df = filtered()
    return f"{len(df):,} records match the current filters."

Because summary reads filtered(), it updates whenever the “Apply filters” button fires, not on every slider move. No extra wiring needed.
