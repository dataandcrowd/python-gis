4.5 Assignment 3: package project briefs

How this assignment works

You will work in pairs. Each pair is assigned one of the five packages described below. Your brief tells you what the package should do, which functions you must implement, and what dataset to use for the demonstration.

Pairs and assignments are announced in the Week 9 lecture. Read your brief carefully before your Week 10 check-in. By Week 10 you should be able to explain the package’s purpose and your planned structure.

What you submit

By the end of Week 12, every pair submits the following.

  • A TestPyPI release of the package (and ideally a production PyPI release).
  • A GitHub repository with the source code, tests, and a working README.
  • A demo notebook that loads the data, calls the package, and produces the requested visualisation.
  • An A1 poster presented at the Week 11 showcase on Tuesday 25 May (B301-G10).
  • A fit interview conducted in the Week 12 lab (about 5 to 10 minutes per person, see the next section).

Fit interview

Each pair member sits a short individual fit interview during the Week 12 lab. The aim is to confirm everyone understands the code their pair has shipped. Expect three short prompts.

  1. Walk us through one function you wrote, line by line, and explain what it returns.
  2. Explain one design choice in your package. Why this CRS, why this filter, why this default? What did you reject and why?
  3. Answer one short technical question on the spot (for example, “what would happen if the input had a different CRS?”).

The interview is not a test of memory. It is a quick check that you actually built and understand what you submitted. Bring your laptop with the package open.

The five package briefs

Each brief follows the same shape. A short rationale, the functions you must implement, the demonstration dataset, and notes on difficulty.

pedestrian-exposure

Given a walking route and a set of environmental layers, calculate cumulative exposure along that path.

Pedestrians are not exposed to the same conditions along every part of a journey. A route through a busy arterial will accumulate more noise and air pollution than one through a park, even if the total distance is similar. This package makes that exposure measurable by joining environmental data layers to the edges of a walking route and summarising the result.

Your package takes an OSMnx-derived route (expressed as a list of node IDs) and one or more spatial layers, such as traffic noise polygons, greenery fraction rasters, or air quality estimates, and returns per-edge exposure values alongside a route-level summary score. Think of it as a weighted integral along a path.

Functions to implement.

load_route(origin, destination, place) fetches a walking route between two addresses using OSMnx and returns a GeoDataFrame of edges with geometries.

add_exposure_layer(route_gdf, layer_gdf, column) spatially joins an attribute from a polygon or raster layer onto each route edge, adding it as a new column.

summarise_exposure(route_gdf) returns a tidy DataFrame of per-edge scores and a single route-level weighted summary.

Demonstration dataset. Use pedestrian corridors from the Auckland hotcity.co.nz dataset as your route input, and NDVI derived from a Sentinel-2 image as a greenery exposure layer. Your demo notebook should show a map of a route coloured by exposure level.

Tip

Start with a simple point-in-polygon join before attempting raster sampling. Get the summary table working first, then add the map.

Note

Difficulty level. Intermediate. The main challenge is handling coordinate reference system alignment across layers.

equitransport

Break down transport accessibility by deprivation quintile and surface equity gaps.

Transport planning that looks only at average accessibility can obscure deep inequalities. A city might have good average PT coverage while the most deprived neighbourhoods remain poorly served. This package connects an accessibility metric to the New Zealand Index of Deprivation (NZDep2018) at SA2 level, then computes how that access is distributed across the population.

Your package takes a GeoDataFrame of SA2 boundaries with an accessibility metric column (for example, the number of PT stops within 400 m walk) and joins it to NZDep2018 scores. It then computes quintile means and a Gini coefficient to quantify how unequally access is distributed.

Functions to implement.

load_nzdep(sa2_gdf) joins NZDep2018 deprivation scores to an SA2-level GeoDataFrame by meshblock or SA2 code.

compute_access(gdf, metric_col) calculates the chosen accessibility metric per SA2 polygon.

equity_summary(gdf) returns a quintile breakdown table and a Gini coefficient, along with a choropleth-ready GeoDataFrame for mapping.

Demonstration dataset. Use Stats NZ SA2 boundaries for the Auckland region alongside a PT stop count derived from the Auckland Transport GTFS static feed. Your demo should produce both a summary table and a choropleth map coloured by deprivation quintile.

Tip

The NZDep2018 data is published by the University of Otago and is freely downloadable as a CSV. You can ship it as a small bundled data file inside your package rather than fetching it at runtime.

Note

Difficulty level. Intermediate. The main challenge is correctly aggregating meshblock-level deprivation scores up to SA2 level.

gtfs-lite

Read a GTFS feed into clean GeoPandas objects with one line of code.

The General Transit Feed Specification (GTFS) is the standard format for public transport schedules worldwide, but parsing it from scratch requires juggling multiple CSVs, handling coordinate systems, and joining several tables together. Existing Python packages for GTFS are either too heavy for introductory use or assume prior knowledge of the format. This package wraps just the most useful parts (stops, routes, and service frequency) into a clean GeoPandas-friendly interface.

Your package reads a standard GTFS zip file and exposes stops, routes, and stop times as GeoDataFrames. It also provides a frequency method that tells you how many services per hour depart from a given stop. Real-time feeds (GTFS-RT) are explicitly out of scope for this package.

Functions to implement.

GTFSFeed(path) is the main class. It loads and lightly validates a GTFS zip file on initialisation.

feed.stops() returns a GeoDataFrame of stop locations with Point geometries in EPSG:4326.

feed.routes() returns route geometries as LineStrings constructed from the shapes table.

feed.frequency(stop_id, day) returns the number of scheduled departures per hour for a given stop on a given day of the week.

Demonstration dataset. Use the Auckland Transport GTFS static feed, which is publicly available for download from the AT Developer Portal. Your demo notebook should map all bus routes in the Waitematā Local Board area and show a frequency table for three stops of your choice.

Tip

Build the class incrementally. Get stops() returning correct geometries before moving on to routes, and leave frequency() until both spatial methods are solid.

Note

Difficulty level. Beginner-friendly. The data is well-structured and the main task is joining and converting existing tables rather than spatial analysis.

treecrown-nz

Measure urban tree canopy coverage and shade along any Auckland street or area.

Urban tree canopy is increasingly recognised as critical infrastructure. It reduces heat stress, improves air quality, and makes walking more comfortable. Auckland Council has invested in LiDAR-derived canopy mapping, but using that data programmatically requires navigating the LINZ Data Service API, clipping geometries, and computing coverage statistics, steps that every researcher ends up writing from scratch. This package automates that workflow.

Your package fetches canopy polygon data for a bounding box from LINZ, then computes coverage percentage for a user-supplied area or along a buffered walking route. The output is a per-polygon or per-segment summary suitable for mapping and further analysis.

Functions to implement.

load_canopy(bbox) fetches the Auckland Council canopy layer from LINZ for a given bounding box and returns a GeoDataFrame of canopy polygons.

canopy_coverage(area_gdf) computes the percentage of each input polygon covered by canopy.

route_shade(route_gdf, buffer_m) buffers each edge of a route by a given distance (in metres) and returns the canopy fraction within that buffer, a proxy for pedestrian shade.

Demonstration dataset. Use the Auckland Council LiDAR-derived canopy layer available via the LINZ Data Service. Your demo notebook should compare canopy coverage across three Auckland suburbs and produce a map showing shade fraction along a walking route of your choice.

Tip

The LINZ API requires an API key. Register for a free account at data.linz.govt.nz and store your key in a .env file. Never hard-code it in your package source.

Note

Difficulty level. Intermediate to ambitious. The LINZ API has some quirks around pagination and layer IDs. Budget time for getting the data access working before the analysis.

pavescore

Pass in a pavement photo, get back a condition score and defect flags.

Pavement condition inspections are currently conducted manually by Auckland Council field staff, a slow and expensive process. Computer vision offers a path to scalable, consistent assessment from street-level imagery. This package takes a pavement photograph (from a file path or a Mapillary URL) and returns a structured condition assessment based on image analysis.

A working basic version uses edge detection and texture analysis to detect surface degradation. A more ambitious version wraps a lightweight pre-trained image classifier. Either approach is valid for this assignment, provided your outputs are consistent and your methodology is clearly documented.

Functions to implement.

score_image(path_or_url) takes a single image and returns a PavementResult dataclass containing an overall score (0 to 100, where 100 is perfect condition), binary defect flags for cracking, surface degradation, and obstruction, and a confidence value.

score_batch(image_list) processes a list of images and returns a summary DataFrame with one row per image.

to_geodataframe(results, coords) takes a list of PavementResult objects and a matching list of (lat, lon) tuples and returns a GeoDataFrame suitable for mapping.

Demonstration dataset. Use Mapillary images sampled along Dominion Road or Queen Street, Auckland. The Mapillary API is free for research use and returns image URLs that your package can consume directly. Your demo notebook should produce a map of scored locations coloured by condition category (good, fair, poor).

Tip

Focus on getting score_image() returning a consistent and sensible output before building the batch and spatial methods. A simple texture-based scorer that works reliably is better than an ambitious classifier that is fragile.

Warning

Image analysis can be computationally slow. Make sure your demo notebook includes a small pre-sampled set of images (10 to 20) rather than fetching hundreds at runtime during the presentation.

Note

Difficulty level. Ambitious. This is the most open-ended brief of the five. You have more design freedom, which also means more decisions to justify in your poster and interview.

Working timeline

A suggested rhythm. Adjust as needed.

Week 9. Read your brief, set up the package skeleton in pairs, draft the public API as a list of function signatures, and implement one function end to end. The Week 9 lab walks you through this.

Week 10. Add tests, write the README, publish to TestPyPI, and start the demo notebook. The Week 10 lab covers pytest patterns, TestPyPI release, poster outlining, and a fit interview rehearsal.

Week 11. Polish the code, finish the demo notebook, and present the A1 poster at the Tuesday 25 May showcase (B301-G10).

Week 12. Publish to production PyPI once the TestPyPI install is fully confirmed. Sit the fit interview during the lab.

Common mistakes to avoid

These come up every year. None of them are fatal, but each one costs you time.

Hard-coded paths. Use importlib.resources or pathlib to find files relative to the package. Never write '/Users/me/Desktop/...' inside the package source.

No error handling on missing data. If a file does not exist or an API key is missing, raise a clear FileNotFoundError or ValueError rather than letting a deep KeyError surface later.

Print statements left in functions. Remove print calls from your final code. Use return values for outputs and let the user decide what to display.

Vague docstrings. Every public function needs a one-line summary, a Parameters section, and a Returns section. NumPy style is the convention. Look at akl-ped-counts for examples.

Tests that only check imports. A test that just confirms from your_package import f is not really a test. Write tests that exercise the function with real-shaped inputs and check the output shape and values.

Forgetting the demo notebook. The notebook is what convinces a reader that your package works on real data. Leave time for it. Run it from a clean kernel before submitting.
